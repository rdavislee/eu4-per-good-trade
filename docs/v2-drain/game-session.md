# B1 — Cyclic node file (V149) — **REFUTED**

**Claim.** "What the design depends on is the *engine's* behaviour on a cyclic file, which is
unverified and load-bearing." The open question was whether the engine tolerates a cycle.

**It does not. It dies.**

## Setup

Mod `pgt_cycle`: vanilla `00_tradenodes.txt` with one block added. Vanilla already has
`sevilla → valencia`; I added `valencia → sevilla`, forming a two-node cycle. The reverse link's
render data was generated by §2.4 item 3's own recipe — reverse the province list, reverse the
control pairs — so this doubled as that item's "verify one hand-flipped link" step, and it
round-tripped correctly:

```
sevilla → valencia                    valencia → sevilla (generated)
  path    = 4546 223 222 221 1295       path    = 1295 221 222 223 4546
  control = 2751,1257  2780,1258        control = 2812,1300  2798,1275
            2798,1275  2812,1300                  2780,1258  2751,1257
```

Verified after writing: 80 blocks, 160 links, the 2-cycle present, everything else byte-faithful.

## Observation

**(a) Does it load?** No. **`EXCEPTION_STACK_OVERFLOW` (C00000FD)**, reproduced on two independent
launches. Crash dumps at `crashes/eu4_20260820_134250/` and `crashes/eu4_20260820_134617/`, each
with `Mods: mod/pgt_cycle.mod` in `meta.yml`.

The stack trace is the diagnosis:

```
Unhandled Exception C00000FD (EXCEPTION_STACK_OVERFLOW) at address 0x00007FF6DDE6A8B4
Stack Trace:
  1 … 1002   eu4.exe (function-name not available)
```

**1002 recorded frames, all at one identical return address.** That is unbounded recursion: the
engine walks the node graph recursively and the cycle never terminates.

**(b) Does `logs/error.log` complain?** Yes, and it names the rule before it dies:

```
[tradenodedefinition.cpp:61]: Valencia=>sevilla ( ERROR: Trade nodes must always be defined
so that an outgoing is defined after in the file, or we get processing errors)
```

**(c) What does the trade mapmode draw?** Nothing — the process never reaches the main menu.

**(d) Does value move along both links?** Unanswerable; there is no running game.

## The control that makes this attributable

A 2-cycle necessarily creates one backwards-declared link, so the crash could in principle be the
*ordering* violation rather than the cycle. It is not:

| build | order violations | cycle | result |
|---|---|---|---|
| vanilla | 0 / 159 | no | loads, runs |
| `pgt_permute` | **159 / 159** | no | **loads, runs** |
| `pgt_cycle` | 1 / 160 | **yes** | **stack overflow, twice** |

159 backwards links do not crash it. One cycle does. **The cycle is the cause.**

## What must change in the spec

> **⚑ This does not restructure §2.4 — it removes an open question and upgrades an assumption to
> a verified fact.**

§3.6 currently reads:

> What the design depends on is the **engine's** behaviour on a cyclic file, which is unverified
> and load-bearing: §2.7 item 13 is the one-file-edit test, and until it runs, acyclicity is
> enforced because we cannot prove the engine tolerates its absence.

It has now run. Replace with the positive result: the engine does not tolerate a cyclic node file
— it recurses without termination and dies with a stack overflow at load
(`tradenodedefinition.cpp:61` warns; 1002 identical frames; reproduced twice). Acyclicity is
enforced because the engine **provably** cannot survive its absence.

- **V149** re-files from `UNSOURCED` to a named observation, and its status flips from "unverified"
  to settled.
- **V150** ("until §2.7 item 13 runs, acyclicity is enforced because we cannot prove the engine
  tolerates its absence") loses its hedge and gains a proof. Acyclicity becomes a hard
  correctness requirement of the emitter, not a precaution.
- **§2.7 item 13 is done** and can be struck from the probe list.
- §3.6's model-side argument (a splice of two acyclic orientations need not be acyclic —
  C444/C445) is untouched and still stands on its own.

# B2 — Permuted declaration order (V096) — **PARTIAL**

**Claim.** "Whether the engine *requires* topological declaration order is open."

**Answer: the engine validates it and complains once per violation, but tolerates it — and I could
not detect any effect on trade values above the engine's own run-to-run noise.**

## Setup

Mod `pgt_permute`: identical links, identical directions, identical everything — only the order of
the 80 node blocks reversed. Vanilla has 0 of 159 links violating sources-first declaration order;
this file has **159 of 159**. The maximal form of the test.

## Observation 1 — the engine checks, and says so

`logs/error.log` contains **exactly 159 lines**, one per backwards link, no more and no less:

```
[tradenodedefinition.cpp:61]: Valencia=>genua ( ERROR: Trade nodes must always be defined
so that an outgoing is defined after in the file, or we get processing errors)
[tradenodedefinition.cpp:61]: Champagne=>genua ( ERROR: … )
[tradenodedefinition.cpp:61]: Sevilla=>valencia ( ERROR: … )
…159 total
```

The count matching my static analysis exactly (159/159) confirms the engine evaluates this
per link at load.

## Observation 2 — it loads and plays anyway

The game reached the main menu, started a Castile 1444 campaign, and ran to 22 December 1444
without incident. Trade functioned: merchants were placed and steering (`Safi 0.58 → to Sevilla`,
`Tunis 0.30 → to Sevilla`), node values populated, arrows drawn. Save
`Castile1444_12_22.eu4` is the artifact.

So the error is a **warning**, not a refusal.

## Observation 3 — the value comparison, and the control that overturned my first read

I compared **all 80 nodes** on five fields, parsed out of save files rather than read off tooltips.
To remove event and tick noise I compared the deterministic **1444.11.11 start state**.

My first result looked decisive: vanilla vs permuted differed on **61 of 80 nodes**. Then I ran the
control — **two identical vanilla runs** — and it collapsed:

| field | VANILLA run 1 vs run 2 (noise) | VANILLA vs PERMUTED (test) |
|---|---|---|
| `total` | 1/79 differ, max **0.012%** | 1/79 differ, max **0.012%** |
| `retention` | 0/80 differ | 0/80 differ |
| `current` | 49/77 differ, max 7.20% | 55/77 differ, max 8.48% |
| `local_value` | 30/79 differ, max 8.96% | 31/79 differ, max 8.46% |
| `outgoing` | 37/66 differ, max 7.19% | 48/66 differ, max 8.40% |

**Two identical vanilla runs disagree on 49 of 80 nodes by up to 8.96%.** The permuted run's
disagreement is the same size and the same shape on every field — on `local_value` it is
*smaller* than the noise. The two deterministic fields, `total` and `retention`, are unaffected by
permutation.

The noise has an obvious source: EU4 randomises AI merchant placement at campaign start, and
merchants are worth +2 power each. The power-dependent fields (`current`, `local_value`,
`outgoing`) inherit that randomness; the structural fields (`total`, `retention`) do not.

**Conclusion: no measurable effect of declaration order on trade values.** I want to be explicit
that this is a null result at a stated precision, not proof of no effect: on the deterministic
fields the bound is tight (≤0.012%), on the power-dependent fields the noise floor is ~9% and
nothing could be resolved below it. I also only measured the start state; the engine's own phrase
"or we get processing errors" may refer to something that manifests later or elsewhere.

## Observation 4 — the arrows do not flip, and the one thing that *does* change

Follow-up run, permuted file, trade mapmode over Iberia/Gibraltar, compared against the same
region and camera under vanilla. **The drawn arrows are identical in direction.** Pixel-diffing
the two captures is not a usable method — a live 3D map has water animation and sub-pixel camera
drift, which put 2.9% of pixels "clearly different" with no arrow having moved — so the
comparison that settles it is the node window's own structural text.

Sevilla node window, vanilla vs permuted:

| | vanilla | permuted |
|---|---|---|
| incoming tabs | `?????`, **Tunis**, **Safi**, `?????` | `?????`, **Safi**, **Tunis**, `?????` |
| outgoing tab | **Valencia** | **Valencia** |
| Castile provincial power | 129.9 (23.7%) | 129.9 (23.7%) |
| Portugal | 88.5 (21.7%) | 88.5 (21.7%) |
| Morocco | 23.4 (−46.9%) | 23.4 (−46.9%) |
| Granada | 11.6 (21.2%) | 11.6 (21.2%) |
| Aragon | 0.0 (8.7%) | 0.0 (8.7%) |
| France | 0.0 (5.1%) | 0.0 (5.1%) |
| Incoming / Local / Outgoing / Total | +1.43 / +7.23 / −0.45 / 8.20 | +1.40 / +7.18 / −0.45 / 8.13 |

Link membership and direction are identical — Safi and Tunis incoming, Valencia outgoing, in both.
Every provincial-power figure and every power share is identical to the digit. Only the
value fields move, by the run-to-run margin already established.

**The one visible effect of declaration order:** the *order of the entries in the incoming list*
follows the file. Vanilla lists `Tunis, Safi`; the reversed file lists `Safi, Tunis`. Same links,
same directions, different enumeration order.

That is a small but genuinely useful result for §1.7 and §2.4: the node window's link lists are
rendered in file declaration order, so an emitter that reorders nodes will reorder what the player
sees in the incoming/outgoing lists — a cosmetic consequence worth knowing about before shipping a
generated file, and one more reason to emit in a stable order.

## What must change in the spec

> **⚑ This is the §2.4 flag, and it is real — but it points the opposite way from what I expected
> an hour ago.**

§2.4 currently opens:

> The engine performs no topological sort — the file must be one.

**Half of that is now verified and half is overstated.** Verified: the engine performs no
topological sort, and it explicitly expects the file to be sorted — it says so in its own error
text, per link. Overstated: "must" implies necessity, and the engine loads, runs and produces
trade values indistinguishable from vanilla's with all 159 links reversed.

Suggested replacement: *"The engine performs no topological sort and validates that the file is
one, logging `tradenodedefinition.cpp:61` once per violating link. Violations are not fatal — a
fully reversed file loads and plays, with node `total` and `retention` unchanged and the
power-dependent fields differing only within the engine's own run-to-run variance — but the
generator emits in sorted order because that is the convention the engine states."*

- **V096** moves from `UNSOURCED`/open to a named observation, status **PARTIAL**: the requirement
  is real as a validated convention, not as a hard constraint.
- **V095** (the shipped file is sorted, 0/159) is unaffected and is now explained: it is sorted
  because the engine asks for it.
- §2.4 item 1 keeps its instruction; only its justification changes, from assumed necessity to
  observed convention.
- **§2.8's "Acyclicity … on the emitted file's declaration order"** keeps its purpose, but for the
  B1 reason (cycles crash the engine), not the B2 reason.

## A finding for §2.8 that nobody asked for

**EU4's own trade values are not reproducible run to run.** Two identical vanilla Castile 1444
starts differ on 49 of 80 nodes by up to 8.96%. §2.8 contains:

| Economy tab vs. overlay | Every displayed trade figure matches the per-good economy **to the ducat** |

Under the mod the DLL overwrites these figures, so the row is about the mod's own consistency
rather than about matching vanilla — but any validation that compares against *stock* EU4 numbers
needs a tolerance, and "to the ducat" is not achievable against a baseline that moves by 9%
between runs. Worth a sentence in §2.8.

# B3 — Does a reversed link actually reverse? (§2.4 item 3) — **CONFIRMED**

This is not one of the five claims in the brief. It is the test the brief's B section implies but
does not name, and it is the **most load-bearing implementation assumption in the whole spec**:
§2.4 item 3 says *"Link reversal — move the `outgoing` block, reverse the `path` province list,
reverse the `control` pairs. Verify one hand-flipped link before writing generator code."* If the
engine will not honour a reversed link, the mod is impossible.

Neither B1 nor B2 tested it. B1 *added* a reverse link (making a cycle, which crashes); B2 kept
every direction identical. So I ran it.

## Setup

Mod `pgt_flip_ordered`: vanilla with `sevilla → valencia` **removed from sevilla** and
`valencia → sevilla` **added to valencia**, path and control reversed by §2.4 item 3's recipe.
Still 159 links, **no cycle**, and valencia's block moved ahead of sevilla's so declaration order
stays sources-first — **0 order violations**, isolating the flip from everything else.

## Observation

**`logs/error.log`: zero non-descriptor lines.** The engine accepts a hand-reversed link silently.

Sevilla node window, vanilla vs flipped:

| | vanilla | flipped |
|---|---|---|
| incoming tabs (left) | `?????`, Tunis, Safi, `?????` | `?????`, Tunis, Safi, `?????`, **Valencia** |
| outgoing tab (right) | **Valencia** | **— none —** |
| Outgoing value | −0.45 | **0** |
| Incoming | +1.43 | +0.84 |
| Total | 8.20 | 8.02 |
| node marker | `1.40 (47%) 8.2 (4)` | `1.40 (50%) 8.0 (5)` |
| countries listed | Castile, Portugal, Morocco, Granada, **Aragon, France** | Castile, Portugal, Morocco, Granada |
| Castile's merchant | steering, "We earn 4.87" | **collecting**, "Ramón Cortés (Collect from Trade)", "We earn 5.22" |

**Valencia moved from the outgoing side to the incoming side, and Sevilla's outgoing group is now
empty.** Sevilla has become an end node — five incoming links, zero outgoing. On the map the
outgoing-value marker that sat on the Málaga coast in vanilla is gone, and the chevrons near the
node now converge on it.

## Why this is the result that matters

The direction change did not just redraw an arrow. **The entire economy rebuilt around it**, and
every consequence is one the spec depends on:

- **The AI switched strategy.** Castile's merchant was steering out of Sevilla; with nowhere
  downstream to steer, it now collects there instead — and earns more doing it (4.87 → 5.22).
  Merchants react to the graph.
- **Propagated power vanished, and with it two countries.** Aragon (14.2) and France (3.3) were in
  Sevilla's power list purely via `Transfers from traders downstream` (see A2). Sevilla now has no
  downstream, so the transfer term is gone and **both countries disappear from the node entirely**.
- **Power shares recomputed throughout** — Castile 23.7% → 8.7%, Portugal 21.7% → 6.7%, Granada
  21.2% → 6.2% — while every *provincial* power figure stayed identical (Castile 129.9, Portugal
  88.5, Morocco 23.4, Granada 11.6). Exactly right: provinces don't move, topology does.

**§2.4 item 3 is verified.** The reversal recipe — move the `outgoing` block, reverse `path`,
reverse `control` — produces a link the engine accepts without complaint and honours completely,
in the arrows, the value flow, the collect/steer decision, and the propagation graph. The spec's
instruction to "verify one hand-flipped link before writing generator code" is now done, and it
passed.

This is the mod's core premise demonstrated end to end: **change direction in the file, and EU4
rebuilds the trade economy around the new direction.** Combined with B1, the constraint on the
generator is exactly one thing — the emitted graph must be **acyclic**. Within that, the engine
will follow whatever directions it is given.

# A2 — Does power appear upstream where a country holds none? (V105) — **REFUTED**

**Claim.** "Whether a country with above-threshold power in X and zero power in upstream Y appears
in Y is unknown (§2.7 item 15)." This is §3.16's cautionary case.

**The tooltip's qualifier is not a precondition. Power propagates into nodes where the country
holds literally nothing.**

## Observation — the clean case

In the **Sevilla** node window, the country power table lists **France**:

| Country | merchant | provincial power | share | total |
|---|---|---|---|---|
| Castile | 0.0 | 129.9 | 23.7% | 140.2 |
| Portugal | 0.0 | 88.5 | 21.7% | 94.9 |
| Morocco | 2.0 | 23.4 | −46.9% | 23.7 |
| Granada | 0.0 | 11.6 | 21.2% | 16.7 |
| Aragon | 2.0 | 0.0 | 8.7% | 14.2 |
| **France** | **0.0** | **0.0** | **5.1%** | **3.3** |

France holds **no provinces** in the Sevilla node and has **no merchant** there (0.0 in both
columns, where Morocco and Aragon show 2.0). Yet France is in the list with 3.3 power.

Hovering France's power gives the engine's own itemisation:

```
Current Trade Power: 3.3
--------------
Transfers from traders downstream: +3.1
And multiplied by 1.05 due to +5.10% Trade Power modifier in this node.
```

**Every point of France's power in Sevilla is propagated from downstream.** There is no base term,
no merchant term, no provincial term — because France has none of those here.

## Corroboration

The same breakdown for **Castile in Safi** (Safi is upstream of Sevilla, where Castile is dominant):

```
Current Trade Power: 27.0
--------------
Merchant Present: +2.0
Base: 2
Transfers from traders downstream: +25.9
And multiplied by 1.08 due to +8.70% Trade Power modifier in this node.
```

Castile's provincial power in Safi is 0.0; 25.9 of its 27.0 is propagation. The engine itemises
`Merchant Present` and `Transfers from traders downstream` as independent additive terms — the
merchant is not a gate on the transfer, which the France case proves outright.

## What must change in the spec

**§1.9 is correct as written and needs no change.** It says the share is received "in **every**
immediately upstream node", with no receiving-side condition. That matches the engine.

What must change is the **claim about the tooltip**:

- **V073** stays CONFIRMED as a *quotation* — `TRADE_POWER_UPSTREAM_DESC` really does say
  "to trade nodes where it already has power". But the spec should record that the qualifier is
  **descriptively false**: it is loose English, not a condition. A country with nothing in the
  upstream node still receives.
- **V105** re-files from `UNSOURCED` to a named observation, status REFUTED as an open concern.
- **V211** currently reads: *"§1.9 still does not carry the tooltip's second qualifier ('where it
  already has power'), pending §2.7 item 15 — the cautionary case is not yet closed."* **It is now
  closed, and §1.9 was right not to carry it.** §3.16's closing paragraph should be rewritten:
  the cautionary case ends not with a correction but with a vindication — the reviewers' text was
  right and the engine's own tooltip was the unreliable source.
- **§2.7 item 15 is done** and can be struck.

There is a nice irony worth one line in §3.16: the audit's own rule is "every engine fact must
carry its source — a file path, a binary string, or a named observation." Here a binary string
*was* the source, and the binary string was wrong. Sources are necessary, not sufficient; a
localisation string describes intent, not behaviour.

# C — Ironman encoding (V084) — **CONFIRMED**

**Claim.** "Ironman saves are binary-encoded."

**Mode: files, by a different route than the brief specified.** Hydrating a OneDrive save is
impossible — the cloud provider is down and opening one raises `The cloud file provider is not
running`. Instead I found **24 readable saves outside OneDrive**, and then generated a 25th.

## The three-way format picture, all on this machine

| sample | n | container | inner magic | ironman |
|---|---|---|---|---|
| Steam Cloud mirror (`Steam/userdata/…/236850/remote/save games/`) | 16 | **ZIP** (`gamestate`, `meta`, `ai`) | **`EU4bin`** | yes |
| Shipped tutorials (`…/Europa Universalis IV/tutorial/`) | 8 | none, single stream | `EU4txt` | no |
| **Generated by me this session, 1.37.5, non-ironman, compress on** | 1 | **ZIP** (same three entries) | **`EU4txt`** | no |

The 16 ironman saves span game versions 1.24.1, 1.28.3, 1.33.3 and 1.35.2. The last row is a save
I made during the B2 run — a current-patch non-ironman control that the other two samples lacked.

## How I established the 16 are ironman

The binary `meta` is a token stream, so "ironman" is not greppable. I decoded it far enough to
align against a text save's field order. A text meta carries exactly **two** booleans between
`dlc_enabled` and `campaign_id`:

```
multi_player=no
not_observer=yes
campaign_id="…"
```

Every binary meta carries exactly **three** `[token][=][bool]` triples in that slot, identical
across all 16 files and all four game versions:

```
(0x3589, 1)   (0x3329, 0)   (0x3317, 1)   then campaign_id
```

Aligning from the end: `0x3329=0` ↔ `multi_player=no`, `0x3317=1` ↔ `not_observer=yes`. The extra
**leading, true** boolean `0x3589` is the field text saves lack — `ironman=yes`. EU4 omits the key
when false, which is why all eight tutorials lack it.

Corroboration: a bare serializer key **`ironman` at `eu4.exe:0x2188f2c`**, in the same string pool
as its meta siblings `savegame_version` (`0x219d83c`), `displayed_country_name` (`0x21e9d04`),
`not_observer` (`0x21d12f4`), `multi_player` (`0x21f2d3c`) and `campaign_id` (`0x21fc79c`).

**Verdict: CONFIRMED.** Ironman → binary. 16 of 16, four versions.

## What must change in the spec — more than the claim

The claim is true, but §2.1's reasoning and §2.2's parser item are both understated.

§2.1: *"the parsers target non-ironman because ironman saves are binary-encoded, not because
ironman is unavailable"* — true, but it implies non-ironman saves are directly readable text.

§2.2 item 2: *"Parser for non-ironman saves — province owner, `base_tax`, …"* — no mention of a
container.

Two corrections, both now verified rather than inferred:

1. **A save is a ZIP container, not a flat file, and the spec never says so.** Three entries
   (`gamestate`, `meta`, `ai`), each with its own magic. The parser must unzip and dispatch per
   entry before reading a token. I hit this directly: my own save tooling had to be written
   against it.
2. **Compression is orthogonal to ironman.** My non-ironman 1.37.5 save is a ZIP of `EU4txt`;
   the ironman saves are ZIPs of `EU4bin`. The magic tracks ironman; the container tracks the
   `compress_saves` setting, which is **on** in this user's `settings.txt`. Consistent with the
   577 OneDrive saves: 572 are under 10 MB where a known-uncompressed text save is 24.6–30.4 MB.

**Suggested §2.2 item 2:** *"Parser for non-ironman saves — a ZIP container whose `gamestate`,
`meta` and `ai` entries each carry their own `EU4txt`/`EU4bin` magic (compression is controlled by
`compress_saves` and is independent of ironman; the magic is what tracks ironman). Read province
owner, `base_tax`, `base_production`, trade good, goods produced, development. Uncompressed
single-stream saves also exist — the shipped tutorials — and must be accepted."*

## What I got wrong, and what caught it

My first B2 reading was that permuted order changed trade values — 61 of 80 nodes differed, which
looked conclusive. It was wrong. The vanilla-vs-vanilla control showed 49 of 80 nodes differing
between two runs of *the same build*, at the same magnitude. Without that control I would have
reported a false positive and pushed a spec change on the strength of it. The lesson generalises:
this project's own §3.16 rule is about provenance, and this was a case where provenance was
impeccable — a real measurement, from a real game, parsed from real save files — and the *number*
was still meaningless without a null comparison.
